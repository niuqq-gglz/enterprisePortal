CHAPTER 1

1. 项目背景、目标与建设方案

1.1 背景

企业信息通常分散在多个业务系统、共享目录、群消息、邮件和个人收藏中。员工需要记住内部组织方式、文件路径或具体联系人，才能找到工作入口与资料。这种方式会导致：

  • 同一内容存在多个副本，员工无法判断哪个版本有效。
  • 新员工依赖口头传递，入职信息获取不稳定。
  • 系统入口和支持渠道分散，重复咨询较多。
  • 产品、业务和部门信息缺少统一说明。
  • 旧链接、旧模板和过期制度难以及时下线。

1.2 产品定位

企业员工门户是员工查找信息、资源和工作入口的统一目录，不替代 OA、HR、CRM、财务、研发平台、NAS 等业务系统。

门户负责回答四类问题：

  • 去哪里： 某个系统、工具或网站从哪里进入。
  • 找什么： 某项制度、流程、表单、模板或培训资料在哪里。
  • 是什么： 某个产品、业务、部门或公司信息是什么。
  • 找谁： 遇到 IT、HR、行政、财务或门户问题时联系谁。

业务办理、数据录入、审批和个人信息查询仍由原业务系统承载。

1.3 一期建设方案概要

一期建设一个部署在受控网络中的静态门户：

  • 前端采用 React + TypeScript + Vite。
  • 内容采用 Markdown + JSON，附件位于仓库 public/files，由 Git 管理。
  • 搜索采用浏览器端目录元数据检索。
  • 构建将页面、搜索索引和附件打入 Nginx 镜像；Compose 按镜像标签部署。
  • 不建设数据库、内容后台、门户账号体系和个性化数据。

上线前置条件： “无门户登录”仅在站点位于企业内网、VPN 或统一访问代理之后时成立。如果站点能够被互联网匿名访问，一期必须增加身份访问层，不能把前端隐藏或未知 URL 当作安全控制。

1.4 关键设计决策

决策项 一期结论
一级导航 首页、应用中心、制度与资料、产品与业务、入职指南、新闻公告、帮助支持
新闻归属 新闻归属“新闻公告”；首页只聚合最新 3–5 条
公告归属 公告归属“新闻公告”；首页展示置顶或有效公告，并提供列表与详情
内容复用 同一正式内容只维护一个详情实体，首页和专题页按稳定 ID 引用
搜索范围 标题、摘要、标签、别名、类型、责任部门；不承诺附件正文搜索
前端框架 React + TypeScript + Vite；如团队改用 Vue，须在启动前形成替代 ADR
内容管理 Markdown/JSON + Git 评审，不建设一期内容后台
资料分类 content/taxonomies/resources.yaml 定义分类 id、显示名、排序、启用状态和默认分类；资料只保存 id
文件发布 源文件与元数据同在 Git（稳定 ID 与版本目录）；通过准入的附件随页面、搜索索引打入 Nginx 镜像
访问边界 内网、VPN 或统一访问代理；全员内容不等于互联网公开内容
后续权限 SSO 和服务端授权在后续阶段实施，不能仅靠前端隐藏菜单

1.5 一期目标

一期目标不是建设“大而全”的数字工作台，而是建立可持续维护的统一目录。

具体目标：

  1. 员工无需知道文件存储位置即可找到常用资料。
  2. 员工可以从一个入口进入常用应用和业务系统。
  3. 新员工能够独立完成基础信息获取。
  4. 每项正式内容都有责任部门、版本和复核日期。
  5. 门户能够以较低成本部署、备份、回滚和迁移。

1.6 成功指标

以下为一期建议目标，最终数值应在内容盘点和基线测试后确认：

指标 建议目标 测量方式
核心查找任务成功率 ≥ 90% 5–8 名跨部门员工完成规定任务
典型资料查找中位耗时 ≤ 60 秒 手册、报销模板、VPN、产品资料等任务测试
高频搜索词零结果率 ≤ 5% Top 20 高频查询测试集
目标结果排名 前 3 位 高频查询人工验收
上线时失效链接 0 自动检查与人工抽查
上线时敏感文件误发布 0 发布清单和打包目录审查
超过复核日期的现行内容 0 按 reviewDate 生成检查清单
移动端核心任务完成率 100% 规定页面与下载任务测试
CHAPTER 2

2. 用户、任务与设计原则

2.1 主要用户

用户类型 主要需求
全体员工 查找应用、制度、模板、产品资料和支持渠道
新员工 了解公司、制度、系统、设备、业务和常见事项
业务与职能部门 发布权威内容，减少重复咨询和错误版本传播
门户维护人员 维护目录、校验内容、发布版本和处理失效资源
运维与安全人员 控制访问边界、部署、备份、回滚和安全检查

一期不根据部门或岗位展示个性化首页，所有用户看到相同的全员视图。

2.2 核心用户任务

用户任务按优先级分为：

P0：必须顺畅完成

  • 打开 OA、HR、邮箱、VPN、报销等常用应用。
  • 找到员工手册、制度、流程、表单和模板。
  • 搜索已知名称或关键词并进入正确结果。
  • 找到 IT、HR、行政和财务支持渠道。

P1：应当完成

  • 了解产品、业务场景和相关资料。
  • 新员工按主题完成入职阅读。
  • 查看有效公告和新闻。
  • 查看资源版本、状态和责任部门。

P2：后续优化

  • 个性化推荐和常用入口。
  • 部门或岗位差异化内容。
  • 附件正文全文检索。
  • 内容订阅、收藏、历史记录和阅读进度。

2.3 设计原则

  1. 按员工任务组织，而不是按内部组织结构堆叠。
  2. 搜索可见且优先，不只提供放大镜图标。
  3. 首页负责聚合，不复制正式内容。
  4. 同一内容只有一个权威详情实体。
  5. 入口名称使用员工语言，避免内部缩写和建设方术语。
  6. 任何页面都应说明下一步动作和支持渠道。
  7. 移动端保留完整核心任务，不把它视为缩小版桌面。
  8. 无结果、无内容、失效和异常状态必须可解释。
  9. 全员可见、内部可访问和互联网公开是不同概念。
  10. 一期不以未来能力为由增加当前实现复杂度。
CHAPTER 3

3. 一期范围与访问边界

3.1 一期包含

  • 首页及七个一级栏目。
  • 应用中心、产品与业务列表（主操作直达配置的外链）；资源、新闻、公告、FAQ 的列表和详情页。
  • 标题、摘要、标签、别名等目录元数据搜索。
  • 公开给全体员工的文件在线查看或下载。
  • 内容版本、状态、责任部门、更新时间和复核日期。
  • 桌面端和移动端响应式页面。
  • Markdown/JSON 与附件维护、Git 评审和静态构建。
  • 含页面、搜索索引和附件的 Nginx 镜像，以及 Compose 部署、备份和回滚。

3.2 一期不包含

  • 门户账号注册、登录和个人资料。
  • 我的待办、工资条、我的申请、收藏和个性化推荐。
  • 部门、岗位、项目或个人级权限。
  • 在线审批、评论、内容上传和审核工作流。
  • 内容管理后台、数据库和通用业务 API。
  • NAS 自动同步、在线写入或服务端文件管理。
  • PDF、Word、Excel 等附件正文全文索引。
  • 业务系统 iframe 嵌入。
  • 组织部门、办公地点和品牌资料专页。

3.3 访问边界

推荐从以下两种方式中选定一种，并在上线评审中记录：

方案 A：统一访问代理，推荐

员工先通过企业统一身份或访问代理完成身份确认，再访问静态门户。门户本身仍不建设账号和权限系统。

适用情况：

  • 企业已有统一身份、零信任或反向代理能力。
  • 门户域名可能从互联网访问。
  • 希望保留静态架构，同时识别访问者是否为员工。

方案 B：内网或 VPN

门户仅绑定内网地址，或只允许通过企业 VPN 访问。

适用情况：

  • 一期时间紧，已有可靠网络边界。
  • 内容全部为全员内部内容，不包含部门级限制。

不接受的方式

  • 公网匿名开放，仅通过“不宣传网址”保护内容。
  • 仅用前端隐藏菜单保护文件。
  • 页面禁止访问，但附件 URL 可以直接访问。
  • 将敏感文件放入静态目录后依赖 robots.txt。

3.4 内容分级

级别 定义 一期处理
公开 可对互联网公开 可发布，但应确认版权与品牌规范
内部 可供全体员工查看 仅在受控访问边界内发布
受限 仅特定部门、岗位或项目可查看 不进入一期静态目录
敏感 涉及个人、客户、财务、密钥或安全配置 禁止发布

CHAPTER 5

5. 全局布局与交互规范

5.1 页面框架

顶部区域

  • 企业 Logo 或门户名称。
  • 七个一级导航入口。
  • 当前一级栏目高亮。
  • 全局搜索入口始终可见。
  • 移动端收敛为菜单按钮，打开后展示完整导航。

一期无用户中心，不显示头像、个人姓名或退出登录。

主内容区

  • 首页使用聚合式布局。
  • 列表页采用标题、筛选、结果区结构。
  • 详情页采用正文与关联内容结构。
  • 二级及详情页显示面包屑。

页脚

  • 门户内容维护渠道。
  • 帮助与反馈入口。
  • 使用说明与内容分级提示。
  • 门户版本和最近发布日期。

5.2 搜索交互

  • 首页首屏使用可见搜索框。
  • 占位文案建议：“搜索应用、制度、模板、产品和常见问题”。
  • 输入后可显示建议词，但一期不强制实现复杂联想。
  • 回车进入搜索结果页。
  • 结果页显示命中字段、内容类型和更新时间。
  • 无结果时提供改写建议、常用入口和反馈入口。

5.3 外链与下载

  • 业务系统和外部网站默认新标签打开。
  • 外链必须显示外链标识。
  • 新标签链接使用 rel="noopener noreferrer"。
  • 下载按钮必须说明文件类型、版本和大小。
  • 工具下载同时展示适用操作系统、来源和校验信息。
  • 不使用含义不清的“点击这里”。

5.4 页面状态

每类页面至少设计以下状态：

状态 设计要求
正常 展示完整内容和主要动作
加载 静态站通常短暂，避免大面积闪烁
空状态 说明暂无内容，并提供其他可用入口
无搜索结果 提供关键词建议、热门入口和反馈
内容失效 说明已归档或停止使用，推荐替代内容
链接异常 提供责任部门与反馈渠道
文件不可用 不保留无效下载按钮，说明处理方式

5.5 响应式策略

桌面端

  • 页面内容最大宽度建议为 1200–1280 px。
  • 首页可采用主内容区加侧栏，但不强制三栏。
  • 列表卡片根据内容密度使用两至三列。

平板端

  • 一级导航允许横向收敛或进入菜单。
  • 双栏逐步降为单栏。
  • 筛选器可折叠，但当前条件必须可见。

手机端

  • 单栏排列。
  • 搜索、常用应用、公告优先。
  • 主要按钮触控区域不小于 44 × 44 px。
  • 表格转换为字段列表或允许明确的横向滚动。
  • 不隐藏版本、状态和责任部门等关键信息。

5.6 可访问性

  • 所有功能可通过键盘完成。
  • 焦点样式清晰可见。
  • 页面有跳过导航入口。
  • 标题层级连续，不以字号替代语义。
  • 图片提供有意义的替代文本。
  • 图标按钮提供可读名称。
  • 文本与背景对比度满足通用可访问性要求。
  • 动效遵循 prefers-reduced-motion。

5.7 文案规范

  • 标题使用员工能够直接理解的名词或任务。
  • 按钮使用“动词 + 对象”，例如“下载报销模板”。
  • 避免“赋能、打造、沉淀、触达”等泛化表达。
  • 缩写首次出现时给出中文解释。
  • 错误信息说明发生了什么、用户可以做什么、联系谁。
  • 状态名称保持一致，不在不同页面混用“停用、下架、失效、废弃”。
CHAPTER 6

6. 页面详细设计

6.1 首页

页面目标

员工在首屏完成搜索，并进入最常用的应用、公告或资料。

推荐模块顺序

  1. 顶部导航
  2. 主搜索区
  3. 常用应用
  4. 公告
  5. 常用资料
  6. 产品与业务入口
  7. 新闻
  8. 入职指南横幅
  9. 帮助支持入口

模块规则

常用应用

  • 展示 6–10 个全员高频入口。
  • 每个入口显示图标、名称和一句话用途。
  • 点击直接打开应用；其余内容进入应用中心。
  • 一期不根据个人使用记录排序。

公告

  • 展示有效、已发布的公告。
  • 置顶公告优先。
  • 显示标题、发布日期、有效期或状态。
  • “查看全部”进入“新闻公告 → 公告”。

常用资料

  • 优先展示员工手册、报销模板、IT 指南和信息安全规范。

7. 内容模型与文件管理

7.1 建模原则

不使用一个巨大对象承载所有内容类型。采用“公共字段 + 类型专属字段”。

7.2 公共字段

字段 必填 说明
id 是 稳定唯一 ID，如 DOC-HR-001
type 是 app、document、product、news、notice、faq 等
title 是 标题
summary 是 一至两句摘要
aliases 否 同义词、简称、旧称
category 是 导航分类。制度与资料填写资料分类配置中的稳定 id，页面展示对应 label
topics 否 业务主题
tags 否 受控标签
audience 是 适用对象，一期通常为全员
owner 是 责任部门
ownerContact 是 团队邮箱、工单或公共渠道
status 是 生命周期状态
updatedAt 是 最近更新时间
reviewDate 是 下次复核日期
securityLevel 是 public、internal、restricted、sensitive
featured 否 是否首页推荐
sortOrder 否 人工排序

status 在界面上的用户文案：

系统状态 用户文案
draft 草稿，不对员工展示
scheduled 待生效
published 有效
archived 已归档
retired 已停止使用
expired 已失效

资料分类配置

制度与资料的分类配置为 content/taxonomies/resources.yaml：

defaultCategory: policy
categories:
  - id: policy
    label: 制度与手册
    sortOrder: 10
    enabled: true
  - id: process
    label: 流程与表单
    sortOrder: 20
    enabled: true
  - id: template
    label: 模板与文件
    sortOrder: 30
    enabled: true
  - id: product
    label: 产品资料
    sortOrder: 40
    enabled: true
  - id: training
    label: 培训与学习
    sortOrder: 50
    enabled: true

规则：

  • id 在配置内唯一，并在后续发布中保持不变。修改 label 或 sortOrder 时，已有资料的 category 保持原 id。
  • label 是员工在页顶看到的名称。
  • defaultCategory 必须指向一条 enabled: true 的分类。
  • 页顶只渲染已启用分类，并按 sortOrder 排列。
  • 资料的 category 必须是已启用分类的 id。出现未知 id、未启用分类、重复 id，或默认分类无效时，构建失败。
  • 停用某个分类时，已发布资料不得继续引用该 id。
  • 该配置只定义页顶分类，不表达文件夹层级，也不对应附件存储路径。

结构化应用和产品可使用 JSON；长篇制度说明、新闻和帮助文章可使用 Markdown Front Matter。

7.5 文件规则

  • 文件路径使用稳定 ID 和版本，不暴露宿主机绝对路径。
  • 文件名使用可理解名称，避免“最终版2-确认版”等非正式版本。
  • 每个现行文件只能有一个有效版本。
  • 旧版进入归档目录，不继续作为默认下载。
  • 安装包、脚本和可执行文件必须经过安全审查。
  • 发布前记录文件大小和校验值。
  • 真源在 Git 仓库；镜像是该次发布的只读副本。

7.6 一期不实现 Storage 服务

一期是静态构建，没有后端执行 save/read/delete 的主体。因此：

  • 保留 storageProvider 和 storageKey 数据契约。
  • 构建流程读取仓库中的文件，将通过准入的附件写入 dist 并打入 Nginx 镜像。
  • Storage 接口、NasStorage 和统一下载 API 放到后续后台阶段。
  • 避免把服务端本地存储与浏览器 localStorage 混淆。
CHAPTER 8

8. 搜索方案

8.1 一期搜索定义

一期搜索是“门户目录搜索”，不是附件全文搜索。

可检索字段：

  • 标题
  • 摘要
  • 别名
  • 标签
  • 业务主题
  • 内容类型
  • 责任部门
  • 产品名称
  • 应用名称
  • FAQ 问题

不检索：

  • PDF、Word、Excel 正文
  • 图片文字
  • 业务系统内部数据
  • NAS 未纳入门户目录的文件

8.2 索引生成

构建脚本读取全部已发布内容，生成只包含可公开给当前门户访问范围的数据索引。

建议流程：

内容文件
  → Schema 校验
  → 资料分类 id 与分类配置对照
  → 状态与安全级别过滤
  → 文本标准化与别名展开
  → 将分类 label 写入索引
  → 生成 search-index.json
  → 与静态站一起发布

资料在索引和搜索结果中展示分类配置里的 label。搜索匹配使用该显示名，资料文件中仍然只保存分类 id。

8.3 排序建议

综合得分按以下优先级计算：

  1. 标题完全匹配
  2. 标题前缀或别名匹配
  3. 标签与主题匹配
  4. 摘要匹配
  5. 首页推荐与人工置顶
  6. 更新时间

不以下载量或点击量作为一期主要排序依据，因为一期可能没有可靠统计数据。

8.4 同义词

维护小规模受控词表，例如：

  • 报销单、费用申请、费用报销
  • VPN、远程访问
  • 员工手册、入职手册
  • OA、办公系统

同义词由门户维护人员根据无结果查询和反馈更新。

8.5 性能边界

当有效目录项数量较小，浏览器端加载索引即可满足需求。上线前应使用真实内容测试：

  • 索引文件体积
  • 首次加载时间
  • 搜索响应时间
  • 低性能终端体验

如果内容规模、正文索引或权限过滤超过浏览器端方案能力，再引入服务端搜索。

9. 技术架构与部署

9.1 技术选型

层级 推荐方案 说明
前端 React + TypeScript + Vite 团队常见、组件化、静态构建简单
路由 React Router 支持列表、详情和专题路由
样式 Tailwind CSS 或现有组件库 启动前二选一，不重复建设
内容 Markdown + JSON 长文与结构化数据各用适合的格式
校验 JSON Schema 或等价机制 构建前检查字段、枚举和引用
搜索 构建时索引 + 浏览器检索 适合一期目录规模
Web 服务 Nginx Alpine 镜像内提供静态页面、附件和缓存
部署 Docker Compose 按镜像标签启动、更新和回滚

如果团队已有成熟 Vue 3 技术栈，可以替换 React，但应在开发启动前形成单一技术决策记录；实施文档不能继续同时保留 React、Next.js 和 Vue 三套候选。

9.2 逻辑架构

员工浏览器
    │
    ▼
内网 / VPN / 统一访问代理
    │
    ▼
Nginx 静态站容器
    ├── HTML / CSS / JavaScript
    ├── 内容数据与搜索索引
    └── 全员可见静态附件

Git 内容仓库
    │
    ├── 内容与 Schema 校验
    ├── 失效链接与文件检查
    ├── 前端构建
    └── Nginx 镜像（页面、搜索索引、附件）
            │
            ▼
      Docker Compose 按镜像标签部署

9.3 构建流程

  1. 安装依赖。
  2. 校验 JSON/Markdown Front Matter。
  3. 校验稳定 ID、状态、引用和文件存在性；资料的 category 必须对应分类配置中已启用的 id。
  4. 过滤草稿、受限和敏感内容。
  5. 生成搜索索引。
  6. 执行前端构建，输出 dist。
  7. 扫描构建目录，确认无密钥、源文件和未批准文件。
  8. 将 dist（含页面、搜索索引和附件）构建为 Nginx 镜像并打上可追溯标签。
  9. 部署测试环境并完成功能验收。
  10. 发布生产环境并执行冒烟检查。

Vite 生产构建输出到 dist，作为 Nginx 镜像的构建输入；vite preview 仅用于本地预览，不应作为生产服务器。

9.4 路由与 Nginx

采用 History 路由时，Nginx 必须将不存在的页面路由回退到 index.html，否则用户刷新详情页会出现 404。

同时应配置：

  • HTML 不长期缓存，确保新版本及时生效。
  • 带内容哈希的静态资源长期缓存。
  • 附件缓存策略与版本目录一致。
  • 合理的安全响应头。
  • Gzip 或 Brotli 压缩。
  • 健康检查路径。
  • 访问日志轮转和磁盘容量控制。

9.5 Docker Compose

生产部署建议使用基础 Compose 文件与生产覆盖文件，明确：

  • 镜像标签对应 Git 提交或发布版本，不使用不可追溯的浮动标签。
  • 容器文件系统只读；业务附件已包含在镜像中。
  • restart 策略。
  • 健康检查。
  • CPU、内存和日志限制。
  • Volume 仅用于日志和备份，不作为内容源。
  • HTTPS 在访问代理还是本机终止。

Docker 官方文档支持在单机生产环境中使用 Compose，并建议使用生产专用覆盖配置。

9.6 发布与回滚

页面、搜索索引和附件打入同一 Nginx 镜像，按镜像标签发布。回滚即切换至上一发布标签，三者一并恢复。

每次发布生成：

  • 镜像标签（对应 Git 提交号或版本号）
  • 构建时间
  • 内容清单
  • 附件清单及校验值
  • 部署记录
CHAPTER 10

10. 安全、隐私与非功能要求

10.1 安全原则

  • 默认不发布，只有通过内容准入检查的资源才进入构建。
  • 受限和敏感内容不进入静态输出目录。
  • 前端隐藏不是授权。
  • 静态站不保存密钥、NAS 凭据和管理凭据。
  • 外链只允许 http 和 https。
  • 所有第三方脚本需要明确来源和用途。

OWASP 建议采用“默认拒绝”的授权思路。后续引入部门权限时，页面、API、搜索结果和文件下载都必须执行服务端授权检查。

10.2 文件安全

一期没有在线上传，但发布安装包、脚本和办公文件仍应：

  • 使用扩展名白名单。
  • 限制文件大小。
  • 校验文件真实类型。
  • 进行恶意文件扫描。
  • 对可执行文件进行来源确认。
  • 记录文件校验值。
  • 禁止把敏感文件放入 Web 根目录。

OWASP 文件上传安全建议可作为未来后台上传功能的设计基线。

10.3 隐私

  • 不展示个人手机号、家庭地址、身份证件等信息。
  • 联系方式优先使用团队邮箱或工单渠道。
  • 组织结构只展示业务需要的信息。
  • 反馈表单提示用户不要提交密码、密钥和客户资料。
  • 如记录访问日志，应明确用途、保留期限和访问人员。

10.4 性能

建议在详细设计阶段确认性能预算：

  • 首屏关键内容优先加载。
  • 图片按显示尺寸压缩。
  • 非首屏图片延迟加载。
  • 搜索索引按实际规模控制体积。
  • 页面不依赖大型运行时服务。
  • 弱网络和普通办公终端可以完成核心任务。

10.5 兼容性

  • 支持企业规定的主流桌面浏览器版本。
  • 支持常见手机浏览器访问。
  • 不依赖仅在单一浏览器可用的关键功能。
  • 下载和外链在浏览器安全策略下行为一致。

10.6 可观测性

一期至少具备：

  • Nginx 访问和错误日志。
  • 容器健康状态。
  • 磁盘空间和日志容量监控。
  • 域名与证书到期提醒。
  • 失效链接定期扫描。
  • 发布后核心页面冒烟检查。

如企业允许，可使用隐私友好的访问统计，了解热门入口和零结果查询；统计方案不得采集不必要的个人信息。

10.7 备份与恢复

备份对象：

  • Git 内容仓库（含 content/ 与 public/files）
  • 部署配置
  • Nginx 镜像
  • 发布清单

定期执行恢复演练，确认备份文件可用，而不是只确认备份任务成功。

CHAPTER 11

11. 内容治理与发布流程

11.1 角色与责任

角色 主要责任
内容负责人 提供内容、确认准确性、版本和适用范围
业务审核人 审核业务表述、制度有效性和发布范围
门户编辑 维护结构化字段、分类、标签和页面质量
安全审核人 审核安装包、敏感信息和异常发布内容
技术发布人 构建、部署、回滚和运行检查
门户产品负责人 管理信息架构、规则、优先级和验收

同一人可以兼任多个角色，但责任必须明确记录。

11.2 发布流程

  1. 内容负责人提交内容和附件。
  2. 门户编辑检查标题、摘要、分类、版本、责任部门和复核日期。
  3. 业务审核人确认内容准确和适用范围。
  4. 安装包、脚本等高风险文件进入安全审核。
  5. 内容通过 Git 变更提交。
  6. 自动执行 Schema、链接、引用和文件检查。
  7. 测试环境预览桌面端和移动端。
  8. 审核通过后构建并发布生产环境。
  9. 发布后检查首页、搜索、详情和下载。
  10. 记录发布版本和结果。

11.3 内容复核

  • 每项正式内容必须有 reviewDate。
  • 到期前生成待复核清单。
  • 未完成复核的内容不应无限期保持“有效”。
  • 公告按有效期自动从首页移除。
  • 失效系统和工具必须提供替代入口或联系渠道。
  • 每季度检查失效链接和无责任人的内容。

11.4 删除与归档

  • 不直接删除仍可能被引用的内容。
  • 先标记归档或停止使用。
  • 详情页说明替代内容。
  • 确认没有外部引用后再决定是否移除。
  • 法规、制度和合同相关文件按企业档案规则处理。
CHAPTER 12

12. 后续演进路线

12.1 阶段一：静态门户

  • Markdown/JSON
  • 静态附件
  • 元数据搜索
  • 受控网络访问
  • Git 评审与发布

12.2 阶段二：内容后台

触发条件：

  • 内容更新频率明显增加。
  • 非技术人员需要直接维护。
  • Git 流程成为发布瓶颈。
  • 需要草稿、审核、定时发布和操作记录。

新增：

  • 内容 API
  • 数据库
  • 编辑与审核后台
  • 发布工作流
  • 操作审计

12.3 阶段三：SSO 与个性化

新增：

  • OIDC 或 SAML 身份接入
  • 门户用户映射
  • 部门、岗位和角色属性
  • 个性化入口与内容推荐

身份认证只解决“用户是谁”，仍需要服务端授权判断“用户能看什么”。

12.4 阶段四：资源权限与统一下载

新增：

  • 服务端资源授权
  • 统一下载 API
  • 权限过滤搜索结果
  • 默认拒绝和最小权限
  • 下载审计

12.5 阶段五：NAS 与全文检索

新增：

  • 后端 Storage 抽象
  • NAS 或对象存储适配器
  • 文件迁移与校验
  • 文档解析和全文索引
  • 权限感知搜索

从一期预留的稳定 ID、storageProvider 和 storageKey 迁移，但不承诺仅修改字段即可完成；引入权限和 NAS 需要后端架构变化。

13. 实施计划、验收与风险

13.1 建议实施阶段

阶段 1：内容盘点与需求冻结

产出：

  • Top 用户任务
  • 首批内容清单
  • 内容分级
  • 一级导航与资料分类配置
  • 责任人和审核人
  • 技术决策记录

退出条件：

  • 访问边界确认。
  • 首批内容责任部门确认。
  • 不存在未处理的受限内容。

阶段 2：详细设计

产出：

  • 首页、列表、详情、搜索、空状态和移动端线框。
  • 组件规范。
  • 页面路由。
  • 内容 Schema。
  • 搜索排序和同义词表。
  • Nginx 与部署设计。

退出条件：

  • 产品、设计、研发和运维共同评审通过。
  • 使用真实内容完成原型走查。

阶段 3：开发与内容制作

产出：

  • 前端页面与组件。
  • 内容校验和索引脚本。
  • 首批正式内容。
  • 测试环境。

退出条件：

  • 核心任务可完成。
  • 构建检查通过。
  • 无严重控制台错误。

阶段 4：部署与试运行

产出：

  • Docker Compose 与生产配置。
  • 访问边界配置。
  • 备份和回滚方案。
  • 用户任务测试报告。

退出条件：

  • 量化验收达标。
  • 敏感文件、断链和无责任内容为零。

阶段 5：上线与复盘

产出：

  • 正式发布版本。
  • 发布清单。
  • 问题处理记录。
  • 下一阶段需求池。

13.2 功能验收

  • 七个一级入口可达。
  • 新闻可从首页进入列表和详情。
  • 公告按状态与有效期展示。
  • 应用入口、外链和下载行为正确。
  • 搜索可检索规定的元数据字段。
  • 资源详情展示版本、状态和责任部门。
  • 制度与资料的页顶分类、顺序和默认项与资料分类配置一致，资料通过分类 id 归类。
  • 归档和失效内容有明确提示。
  • 桌面端和移动端均可完成核心任务。

13.3 安全验收

  • 门户无法绕过既定网络或访问代理边界匿名访问。
  • 受限和敏感内容未进入静态构建目录。
  • 页面与附件访问范围一致。
  • 仓库和镜像中不存在密钥与管理凭据。
  • 安装包、脚本和可执行文件完成审核。
  • 外链协议、打开方式和安全属性符合规则。

13.4 运维验收

  • Docker Compose 可启动、停止和更新。
  • 容器健康检查可用。
  • 深层路由刷新不会出现 404。
  • 切换镜像标签即可整体回滚页面、搜索索引和附件。
  • 备份可以恢复。
  • 日志不会无限占用磁盘。
  • 域名和 HTTPS 终止位置明确。

13.5 上线门槛

以下条件全部满足后方可上线：

  1. 访问边界确认并完成验证。
  2. 一级导航、资料分类配置和内容唯一归属冻结。
  3. 首批内容清单、责任人和审核人完整。
  4. 关键页面和移动端设计完成评审。
  5. 技术栈、路由、搜索方案冻结；附件随镜像发布。
  6. 任务测试达到约定指标。
  7. 断链、敏感文件和无责任内容为零。
  8. 备份、回滚和冒烟检查完成演练。

13.6 主要风险

风险 影响 应对
把内部内容部署为公网匿名站点 信息泄露 上线前验证网络或统一访问代理
栏目重复保存同一资料 版本冲突 唯一实体 + 稳定 ID 关联
搜索承诺包含附件正文 用户预期落差 明确一期只检索目录元数据
多套技术选项长期不决 设计和估时反复 启动前冻结技术 ADR
内容责任人不明确 内容快速过期 owner、reviewDate 和复核清单
附件与页面不同步 下载错误版本 三者打入同一镜像，按标签发布和回滚
首页模块过多 高频任务被稀释 搜索和常用入口优先，限制模块数量
静态站缺少使用数据 无法判断效果 任务测试、反馈和合规统计相结合

home:

  - 全体员工
owner: 人力资源部门
ownerContact: hr@example.com
status: published
securityLevel: internal
version: "2.1"

storageProvider: local
