# 1. 项目背景、目标与建设方案

## 1.1 背景

企业信息通常分散在多个业务系统、共享目录、群消息、邮件和个人收藏中。员工需要记住内部组织方式、文件路径或具体联系人，才能找到工作入口与资料。这种方式会导致：

- 同一内容存在多个副本，员工无法判断哪个版本有效。
- 常用资料依赖口头传递，获取不稳定。
- 系统入口分散，重复查找较多。
- 新闻、公告和常用资料缺少统一入口。
- 旧链接、旧模板和过期制度难以及时下线。



## 1.2 产品定位

企业员工门户是员工查找信息、资源和工作入口的统一目录，不替代 OA、HR、CRM、财务、研发平台、NAS 等业务系统。

门户负责回答四类问题：

- **去哪里：** 某个系统从哪里进入。
- **找什么：** 某项制度、流程、表单、模板或培训资料在哪里。
- **看什么：** 有哪些新闻和公告。
- **什么时候：** 公历、农历、节假日安排，以及天气。

业务办理、数据录入、审批和个人信息查询仍由原业务系统承载。

## 1.3 一期建设方案概要

一期建设员工门户。应用、资料和公告须登录后使用。登录前后首页使用同一布局。新闻和公告由后台维护。不建设个性化数据。

- 前端采用 **React + TypeScript + Vite**。
- 使用 `@ggquanta.com` 邮箱注册后，再用邮箱和密码登录。
- 应用、资料和日历的目录采用 **Markdown + JSON**，由 Git 管理。资料文件是 NAS 上的链接。
- 新闻和公告在后台新建、编辑、发布和下线，保存在数据库。
- 登录前搜索只查已公开新闻，由接口查询数据库。登录后搜索检索应用、资料、新闻和公告的目录元数据。
- 构建将页面和静态搜索索引打入 Nginx 镜像；Compose 按镜像标签部署。
- 用户、新闻和公告保存在同一 PostgreSQL。不建设应用、资料和日历的内容后台。



## 1.4 关键设计决策


| 决策项  | 一期结论                                                                  |
| ---- | --------------------------------------------------------------------- |
| 页面导航 | 不设导航菜单。登录前后首页使用同一布局。登录前展示搜索、新闻、日历、天气                           |
| 栏目进入 | 各模块提供「查看全部」，进入该栏目的全部数据                                                |
| 新闻归属 | 新闻独立成栏目，不设分类；首页只聚合最新 3–5 条。登录前只展示已公开新闻                                 |
| 公告归属 | 公告独立成栏目。首页按发布时间展示，可置顶。不设详情页，点击预览文件。须登录后查看                       |
| 日历   | 含公历、农历和节假日安排；首页为摘要，查看全部进入日历页。登录前可查看                                    |
| 天气   | 展示配置城市的天气；首页为摘要，查看全部进入天气页。登录前可查看                                       |
| 内容复用 | 同一正式内容只维护一个详情实体，首页按稳定 ID 引用                                           |
| 搜索范围 | 登录前只查已公开新闻的标题、摘要、标签。登录后增加应用、资料和公告。不检索 NAS 文件正文                      |
| 前端框架 | React + TypeScript + Vite；                                            |
| 内容管理 | 应用、资料、日历用 Markdown/JSON + Git。新闻和公告用后台管理，不设分类                       |
| 数据访问 | 用户、记住登录凭证、新闻和公告经 Drizzle 访问 PostgreSQL                                 |
| 资料分类 | `content/taxonomies/resources.yaml` 定义分类 id、显示名、排序、启用状态和默认分类；资料只保存 id |
| 资料文件 | 标题、分类、文件名、大小、更新时间和链接写在 Git。点击打开 NAS 上的 https 地址。文件不进入门户镜像 |
| 登录   | `@ggquanta.com` 先注册再登录。注册验证邮箱，登录使用密码。人机验证用 ALTCHA                     |
| 登录前  | 与登录后首页同一布局。展示搜索、已公开新闻、日历、天气，以及注册和登录入口                                 |
| 访问边界 | 内部页面须登录后访问。资料文件由 NAS 控制访问；全员内容不等于互联网公开内容                               |
| 后续权限 | 部门级授权在后续阶段实施，不能仅靠前端隐藏入口                                               |




## 1.5 一期目标

一期目标不是建设“大而全”的数字工作台，而是建立可持续维护的统一目录。

具体目标：

1. 员工无需知道文件存储位置即可找到常用资料。
2. 员工可以从一个入口进入常用应用。
3. 门户能够以较低成本部署、备份、回滚和迁移。



## 1.6 成功指标

以下为一期建议目标，最终数值应在内容盘点和基线测试后确认：


| 指标          | 建议目标   | 测量方式                  |
| ----------- | ------ | --------------------- |
| 核心查找任务成功率   | ≥ 90%  | 5–8 名跨部门员工完成规定任务      |
| 典型资料查找中位耗时  | ≤ 60 秒 | 手册、报销模板、VPN 等任务测试     |
| 高频搜索词零结果率   | ≤ 5%   | Top 20 高频查询测试集        |
| 目标结果排名      | 前 3 位  | 高频查询人工验收              |
| 上线时失效链接     | 0      | 自动检查与人工抽查             |
| 上线时敏感文件误发布  | 0      | 发布清单和打包目录审查           |
| 移动端核心任务完成率  | 100%   | 规定页面与打开资料任务测试         |

# 2. 用户、任务与设计原则



## 2.1 主要用户


| 用户类型    | 主要需求                   |
| ------- | ---------------------- |
| 全体员工    | 查找应用、资料、新闻、公告，并查看日历和天气 |
| 内容维护人员  | 在后台发布新闻和公告，并维护资料       |
| 门户维护人员  | 维护目录、校验内容、发布版本和处理失效资源  |
| 运维与安全人员 | 控制访问边界、部署、备份、回滚和安全检查   |


一期不根据部门或岗位展示个性化首页，所有用户看到相同的全员视图。

## 2.2 核心用户任务

用户任务按优先级分为：

### P0：必须顺畅完成

- 打开 OA、HR、邮箱、VPN、报销等常用应用。
- 使用 `@ggquanta.com` 注册并登录。
- 找到员工手册、制度、流程、表单和模板。
- 搜索已知名称或关键词并进入正确结果。
- 查看新闻和公告。
- 查看日历（含农历和节假日安排）和天气。



### P1：应当完成

- 按分类浏览全部应用和资料。
- 打开资料文件。



### P2：后续优化

- 个性化推荐和常用入口。
- 部门或岗位差异化内容。
- 自动读取 NAS 上的目录和文件。
- NAS 文件正文全文检索。
- 内容订阅、收藏、历史记录和阅读进度。



## 2.3 设计原则

1. **按员工任务组织，而不是按内部组织结构堆叠。**
2. **搜索可见且优先，不只提供放大镜图标。**
3. **首页负责聚合，不复制正式内容。**
4. **同一内容只有一个权威详情实体。**
5. **入口名称使用员工语言，避免内部缩写和建设方术语。**
6. **需要跟进时标明下一步动作。**
7. **移动端保留完整核心任务，不把它视为缩小版桌面。**
8. **无结果、无内容、失效和异常状态必须可解释。**
9. **全员可见、内部可访问和互联网公开是不同概念。**
10. **一期不以未来能力为由增加当前实现复杂度。**

# 3. 一期范围与访问边界



## 3.1 一期包含

- 未登录首页与登录后首页同一布局。未登录展示搜索、已公开新闻、日历、天气。
- 登录后首页在相同位置增加常用应用、公告、资料。
- 首页下方六个模块：常用应用、新闻、公告、资料、日历、天气。登录前不展示常用应用、公告、资料。
- 各模块「查看全部」进入对应栏目：应用列表，新闻列表和详情，公告列表，资料列表，日历页，天气页。
- 门户页面不设导航菜单。
- 标题、摘要、标签、别名等目录元数据搜索。
- 资料目录：标题、分类、文件名、大小、更新时间，以及 NAS 上的 https 链接。
- 新闻与公告后台：新建、编辑、发布、下线。
- 桌面端和移动端响应式页面。
- 应用、资料、日历的 Markdown/JSON、Git 评审和静态构建。
- 含页面和静态搜索索引的 Nginx 镜像，以及 Compose 部署、备份和回滚。
- `@ggquanta.com` 注册、登录、改密和记住登录。
- 新闻、公告和用户数据库及其备份。



## 3.2 一期不包含

- 个人资料与用户中心。
- 我的待办、工资条、我的申请、收藏和个性化推荐。
- 部门、岗位、项目或个人级权限。
- 在线审批和评论。
- 应用、资料、日历的在线内容后台。
- 通用业务 API。
- 自动读取 NAS 目录和文件。
- 服务端写入 NAS，或在门户内管理 NAS 文件。
- PDF、Word、Excel 等文件正文全文索引。
- 业务系统 iframe 嵌入。
- 组织部门、办公地点和品牌资料专页。
- 导航菜单。
- 个人日程、会议。
- 按个人定位的天气。



## 3.3 注册与登录

只接受 `@ggquanta.com`。服务端将邮箱转为小写后校验后缀。其他域名不能注册，也不能登录。管理员可导入账号，并标记必须改密。

### 注册

1. 填写企业邮箱，完成人机验证。
2. 向该邮箱发送验证码，验证通过后由用户设置密码。
3. 密码按策略校验，只以哈希写入 PostgreSQL。
4. 未完成验证码或未设密码的记录不能登录。



### 登录

1. 完成人机验证。
2. 填写邮箱和密码。服务端先校验人机结果，再校验账号和密码。
3. `mustChangePassword` 为真时，只能进入改密页。自己注册并已设密码的账号，该标记为否。
4. 管理员重置或批量导入的账号，该标记为真。改密成功后作废该用户已有会话，须用新密码再登录。
5. 登录成功后签发记住登录凭证。凭证仍有效时直接进入门户。

忘记密码由管理员重置，并标记必须改密。连续失败后锁定一段时间。

### 记住登录

- 记住的是登录状态，不在浏览器保存密码。
- Cookie 为 `HttpOnly`、`Secure`、`SameSite=Lax`。
- 有效期 14 天。退出、停用或改密后，旧凭证作废。
- 凭证只在 PostgreSQL 保存哈希。会话校验可用 Redis。



### 人机验证

采用自建 ALTCHA，与官网后台相同。

- 注册页和登录页使用 `altcha-widget`，中文，不自动通过。
- 挑战为 `PBKDF2/SHA-256`，计算成本 `5000`，10 分钟过期。
- 密钥为 `ALTCHA_HMAC_SECRET`。正式环境必须配置；未配置时仅允许本地降级。
- 解答为空或校验失败时拒绝请求，并要求重新验证。
- 单进程时，已用解答记在内存。多副本时写入 Redis。



### 密码

- 至少 8 位，不超过 128 位，须同时含字母、数字和特殊字符。
- 只存哈希，不写日志，不进入前端包。



### 账号字段


| 字段                 | 说明                 |
| ------------------ | ------------------ |
| email              | `@ggquanta.com`，唯一 |
| passwordHash       | 密码哈希               |
| mustChangePassword | 是否必须改密             |
| status             | 启用或停用              |
| canManageContent   | 能否进入新闻与公告后台        |
| lastLoginAt        | 最近登录时间             |




### 登录前展示

- 与登录后首页使用同一页头和模块位置。
- 页头为 Logo、搜索、注册和登录。
- 搜索、已确认为公开的新闻、日历、天气。
- 新闻、日历、天气可「查看全部」。

登录前不展示常用应用、资料和公告。未登录直接打开这些栏目时，先进入登录。

登录前搜索由接口查询数据库，只返回已发布且级别为公开的新闻。不读取登录后的全量搜索索引。

### 相关技术


| 用途         | 技术              |
| ---------- | --------------- |
| 注册与登录接口    | Hono            |
| 用户与记住登录凭证  | PostgreSQL      |
| 数据访问       | Drizzle         |
| 邮箱验证码与会话校验 | Redis           |
| 人机验证       | ALTCHA          |
| 请求校验       | Zod             |
| 会话凭证       | HttpOnly Cookie |




### 不接受的方式

- 公网匿名开放内部内容，仅通过“不宣传网址”保护。
- 仅用前端隐藏入口保护内部页面。
- 把资料文件放进门户站点，使未登录即可下载。
- 资料使用 `\\` 路径，或非 https 链接。
- 接受非 `@ggquanta.com` 的注册或登录。
- 明文保存密码，或只在前端校验邮箱后缀和人机验证。

# 5. 全局布局与交互规范



## 5.1 页面框架



### 顶部区域

- 企业 Logo 或门户名称。
- 不设导航菜单，不提供菜单按钮。
- 全局搜索入口在登录前后都位于页头。

登录前页头显示注册和登录。登录后显示企业邮箱和退出。一期无用户中心。

### 主内容区

- 登录前后首页使用同一模块顺序。登录前只展示新闻、日历、天气。
- 栏目页从对应模块的「查看全部」进入。
- 列表页采用标题、筛选、结果区结构。
- 详情页采用正文与关联内容结构。
- 栏目页和详情页显示面包屑，可返回首页。



### 页脚

- 门户内容维护渠道。
- 使用说明与内容分级提示。
- 门户版本和最近发布日期。



## 5.2 搜索交互

- 首页首屏使用可见搜索框，位置在登录前后相同。
- 登录前占位文案为「搜索新闻」。回车后只返回已公开新闻。
- 登录后占位文案为「搜索应用、制度、模板、新闻和公告」。
- 输入后可显示建议词，但一期不强制实现复杂联想。
- 回车进入搜索结果页。
- 结果页显示命中字段、内容类型和更新时间。
- 无结果时提供改写建议和常用入口。未登录不提供内部入口。



## 5.3 外链

- 业务系统和外部网站默认新标签打开。
- 外链必须显示外链标识。
- 新标签链接使用 `rel="noopener noreferrer"`。
- 资料通过登记的 https 链接打开，并显示外链标识。
- 应用通过链接打开，不在门户内提供安装包下载。
- 不使用含义不清的“点击这里”。



## 5.4 页面状态

每类页面至少设计以下状态：


| 状态    | 设计要求              |
| ----- | ----------------- |
| 正常    | 展示完整内容和主要动作       |
| 加载    | 静态站通常短暂，避免大面积闪烁   |
| 空状态   | 说明暂无内容，并提供其他可用入口  |
| 无搜索结果 | 提供关键词建议和热门入口      |
| 链接异常  | 说明链接不可用，并给出可用入口   |
| 文件不可用 | 不保留无效链接，说明处理方式    |




## 5.5 响应式策略



### 桌面端

- 页面内容最大宽度建议为 1200–1280 px。
- 首页可采用主内容区加侧栏，但不强制三栏。
- 列表卡片根据内容密度使用两至三列。



### 平板端

- 双栏逐步降为单栏。
- 筛选器可折叠，但当前条件必须可见。



### 手机端

- 单栏排列。
- 搜索、常用应用、公告优先，其下为资料、日历和天气。
- 主要按钮触控区域不小于 44 × 44 px。
- 表格转换为字段列表或允许明确的横向滚动。
- 手机端保留列表中的标题、文件名和打开操作。



## 5.6 可访问性

- 所有功能可通过键盘完成。
- 焦点样式清晰可见。
- 页面有跳至主内容的入口。
- 标题层级连续，不以字号替代语义。
- 图片提供有意义的替代文本。
- 图标按钮提供可读名称。
- 文本与背景对比度满足通用可访问性要求。
- 动效遵循 `prefers-reduced-motion`。



## 5.7 文案规范

- 标题使用员工能够直接理解的名词或任务。
- 按钮使用“动词 + 对象”，例如“打开员工手册”。
- 避免“赋能、打造、沉淀、触达”等泛化表达。
- 缩写首次出现时给出中文解释。
- 错误信息说明发生了什么、用户可以做什么。

# 7. 内容模型与文件管理



## 7.1 建模原则

不使用一个巨大对象承载所有内容类型。采用“公共字段 + 类型专属字段”。

## 7.2 公共字段


| 字段            | 必填    | 说明                                   |
| ------------- | ----- | ------------------------------------ |
| id            | 是     | 稳定唯一 ID，如 `DOC-HR-001`               |
| type          | 是     | app、document、news、notice             |
| title         | 是     | 标题                                   |
| summary       | 应用、新闻 | 一至两句摘要。资料和公告不填                       |
| aliases       | 否     | 同义词、简称、旧称。资料不填                       |
| category      | 资料、应用 | 资料取分类配置中的 id，应用取应用分类。新闻、公告不使用        |
| topics        | 否     | 主题。资料不填                              |
| tags          | 否     | 受控标签。新闻、公告、资料不使用                     |
| audience      | 应用    | 适用对象。资料不填                            |
| updatedAt     | 是     | 最近更新时间                               |
| securityLevel | 是     | public、internal、restricted、sensitive |
| featured      | 否     | 是否首页推荐                               |
| sortOrder     | 否     | 人工排序                                 |


### 资料分类配置

资料的分类配置为 `content/taxonomies/resources.yaml`：

```yaml
defaultCategory: policy
categories:
  - id: policy
    label: 制度与手册
    sortOrder: 10
    enabled: true
  - id: process
    label: 流程与表单
    sortOrder: 20
    enabled: true
  - id: template
    label: 模板与文件
    sortOrder: 30
    enabled: true
  - id: training
    label: 培训与学习
    sortOrder: 40
    enabled: true
```

规则：

- `id` 在配置内唯一，并在后续发布中保持不变。修改 `label` 或 `sortOrder` 时，已有资料的 `category` 保持原 id。
- `label` 是员工在页顶看到的名称。
- `defaultCategory` 必须指向一条 `enabled: true` 的分类。
- 页顶只渲染已启用分类，并按 `sortOrder` 排列。
- 资料的 `category` 必须是已启用分类的 `id`。出现未知 id、未启用分类、重复 id，或默认分类无效时，构建失败。
- 停用某个分类时，目录中的资料不得继续引用该 id。
- 该配置只定义页顶分类，不表达文件夹层级，也不对应 NAS 目录。



## 7.3 类型专属字段



### 应用

- `url`：目标链接，必填
- `loginNote`
- `maintainer`：维护部门，不在列表卡片展示



### 文件与资料

- `url`：NAS 上的 https 链接，必填
- `fileName`
- `fileSize`



### 日历

节假日与调休写入 `content/calendar/holidays.yaml`，不使用上述公共内容字段。

- `date`
- `name`
- `type`：`holiday`（放假）、`workday`（调休上班）

农历由现成历法库换算，不逐日入库。天气不入库。

### 公告

保存在数据库，不写入 Git。不设详情页。

- `publishAt`
- `pinned`
- `url`：公告文件的 https 链接，必填



### 新闻

保存在数据库，不写入 Git。

- `publishAt`
- `coverImage`
- `body`
- `relatedNewsIds`



## 7.4 内容目录建议

```text
content/
  taxonomies/
    resources.yaml
  apps/
  resources/
  calendar/
    holidays.yaml
public/
  images/
scripts/
  validate-content.*
  build-search-index.*
```

应用和资料使用 JSON。日历节假日使用 YAML。新闻和公告保存在数据库。资料文件不放在仓库中。

## 7.5 资料文件

- 每条资料登记一条 https 链接，指向 NAS 上的一个文件。
- 链接须能在公司网络或 VPN 内由浏览器打开。
- 不使用 `\\nas\...` 这类路径。
- 标题、分类、文件名、大小和更新时间写在 Git。文件内容以 NAS 为准。
- 每个现行资料只有一个有效链接。旧链接不作为默认入口。
- 链接失效时说明不可用，不保留无效按钮。
- 安装包、脚本和可执行文件须确认来源后再登记链接。

## 7.6 一期不读取 NAS 目录

- 不在服务端列出或同步 NAS 目录。
- 构建只发布页面和搜索索引，不把资料文件写入镜像。
- 自动读取 NAS 目录、统一下载 API 放到后续阶段。
- 新闻封面在后台上传，不走资料链接。

# 8. 搜索方案



## 8.1 一期搜索定义

一期搜索是“门户目录搜索”，不是 NAS 文件全文搜索。

可检索字段：

- 标题
- 摘要
- 别名
- 标签
- 主题
- 内容类型
- 应用名称

不检索：

- PDF、Word、Excel 正文
- 图片文字
- 业务系统内部数据
- NAS 未纳入门户目录的文件



## 8.2 索引生成

构建脚本读取全部已发布内容，生成只包含可公开给当前门户访问范围的数据索引。

建议流程：

```text
内容文件
  → Schema 校验
  → 资料分类 id 与分类配置对照
  → 状态与安全级别过滤
  → 文本标准化与别名展开
  → 将分类 label 写入索引
  → 合并已发布的新闻和公告
  → 生成 search-index.json
  → 与静态站一起发布
```

资料在索引和搜索结果中展示分类配置里的 `label`。搜索匹配使用该显示名，资料文件中仍然只保存分类 `id`。新闻和公告发布或下线后更新登录后的索引。

登录前搜索不使用这份索引。接口只查询已发布且级别为公开的新闻。

## 8.3 排序建议

综合得分按以下优先级计算：

1. 标题完全匹配
2. 标题前缀或别名匹配
3. 标签与主题匹配
4. 摘要匹配
5. 首页推荐与人工置顶
6. 更新时间

不以下载量或点击量作为一期主要排序依据，因为一期可能没有可靠统计数据。

## 8.4 同义词

维护小规模受控词表，例如：

- 报销单、费用申请、费用报销
- VPN、远程访问
- 员工手册、手册
- OA、办公系统

同义词由门户维护人员根据无结果查询和反馈更新。

## 8.5 性能边界

当有效目录项数量较小，浏览器端加载索引即可满足需求。上线前应使用真实内容测试：

- 索引文件体积
- 首次加载时间
- 搜索响应时间
- 低性能终端体验

如果内容规模、正文索引或权限过滤超过浏览器端方案能力，再引入服务端搜索。

# 9. 技术架构与部署



## 9.1 技术选型


| 层级     | 推荐方案                                 | 说明                               |
| ------ | ------------------------------------ | -------------------------------- |
| 前端     | React + TypeScript + Vite            | 团队常见、组件化、静态构建简单                  |
| 路由     | React Router                         | 首页、列表、详情、日历、天气、注册、登录和改密          |
| 样式     | Tailwind CSS 或现有组件库                  | 启动前二选一，不重复建设                     |
| 内容     | Markdown + JSON；新闻、公告和用户用 PostgreSQL | 应用、资料、日历在 Git；新闻、公告和用户在同一数据库     |
| 校验     | JSON Schema 或等价机制                    | 构建前检查字段、枚举和引用                    |
| 搜索     | 登录后：构建时索引 + 发布后更新。登录前：查询数据库中的已公开新闻 | 登录后索引含应用、资料、新闻和公告。登录前不读取该索引 |
| 登录接口   | Hono                                 | 注册、登录、改密、会话校验；天气转发；新闻与公告接口       |
| 人机验证   | ALTCHA                               | 自建挑战。正式环境配置 `ALTCHA_HMAC_SECRET` |
| 会话     | Redis；记住登录凭证在 PostgreSQL             | Redis 保存邮箱验证码和短时会话校验。密码只存哈希      |
| 登录校验   | Zod                                  | 邮箱后缀、密码策略和人机验证结果                 |
| 数据库    | PostgreSQL                           | 新闻、公告、用户和记住登录凭证；Compose 内独立数据卷   |
| 数据访问   | Drizzle ORM                          | Hono 经 Drizzle 访问上述数据。Git 中的静态内容不经过 Drizzle |
| Web 服务 | Nginx Alpine                         | 镜像内提供静态页面和缓存                     |
| 部署     | Docker Compose                       | 按镜像标签启动、更新和回滚                    |


## 9.2 逻辑架构

```text
员工浏览器
    │
    ├── 打开资料链接 → NAS（https，公司网络或 VPN）
    ▼
Nginx
    ├── 公开首页
    └── 登录后的页面与搜索索引
            │
            ▼
      Hono
        ├── 公开新闻搜索 → Drizzle → PostgreSQL
        ├── 注册、登录、改密与记住登录 → Drizzle → PostgreSQL
        ├── 新闻与公告接口 → Drizzle → PostgreSQL
        ├── 邮箱验证码与会话校验 → Redis
        └── 天气转发

Git 内容仓库
    │
    ├── 内容与 Schema 校验
    ├── 失效链接检查
    ├── 前端构建
    └── Nginx 镜像（页面、搜索索引）
            │
            ▼
      Docker Compose 按镜像标签部署
```



## 9.3 构建流程

1. 安装依赖。
2. 校验 JSON/Markdown Front Matter。
3. 校验稳定 ID、引用和资料链接；资料的 `category` 必须对应分类配置中已启用的 `id`。链接须为 https。
4. 过滤受限和敏感内容。
5. 生成搜索索引。
6. 执行前端构建，输出 `dist`。
7. 扫描构建目录，确认无密钥、源文件和未批准文件。
8. 将 `dist`（含页面和搜索索引）构建为 Nginx 镜像并打上可追溯标签。
9. 部署测试环境并完成功能验收。
10. 发布生产环境并执行冒烟检查。

Vite 生产构建输出到 `dist`，作为 Nginx 镜像的构建输入；`vite preview` 仅用于本地预览，不应作为生产服务器。

## 9.4 路由与 Nginx

采用 History 路由时，Nginx 必须将不存在的页面路由回退到 `index.html`，否则用户刷新详情页会出现 404。

同时应配置：

- HTML 不长期缓存，确保新版本及时生效。
- 带内容哈希的静态资源长期缓存。
- 合理的安全响应头。
- Gzip 或 Brotli 压缩。
- 健康检查路径。
- 访问日志轮转和磁盘容量控制。



## 9.5 Docker Compose

生产部署建议使用基础 Compose 文件与生产覆盖文件，明确：

- 镜像标签对应 Git 提交或发布版本，不使用不可追溯的浮动标签。
- 容器文件系统只读。资料文件在 NAS，不在镜像中。
- `restart` 策略。
- 健康检查。
- CPU、内存和日志限制。
- PostgreSQL 使用独立数据卷，并纳入备份。库内含新闻、公告和用户。
- 其余 Volume 用于日志和备份，不作为应用与资料的内容源。
- HTTPS 在访问代理还是本机终止。

Docker 官方文档支持在单机生产环境中使用 Compose，并建议使用生产专用覆盖配置。

## 9.6 发布与回滚

页面与搜索索引按镜像标签回滚。新闻、公告和用户按数据库备份恢复。资料文件在 NAS，不随镜像回滚。

每次发布生成：

- 镜像标签（对应 Git 提交号或版本号）
- 构建时间
- 内容清单
- 资料链接清单
- 部署记录

# 10. 安全、隐私与非功能要求



## 10.1 安全原则

- 默认不发布，只有通过内容准入检查的资源才进入构建。
- 受限和敏感内容不进入静态输出目录，也不写入新闻与公告库。
- 新闻与公告的写操作只允许 `canManageContent` 为真的账号。
- 前端隐藏不是授权。
- 静态站不保存密钥、NAS 凭据和管理凭据。
- `ALTCHA_HMAC_SECRET` 与密码哈希不进入前端包。
- 外链只允许 `http` 和 `https`。
- 所有第三方脚本需要明确来源和用途。

OWASP 建议采用“默认拒绝”的授权思路。后续引入部门权限时，页面、API、搜索结果和文件下载都必须执行服务端授权检查。

## 10.2 文件安全

安装包、脚本和办公文件不上传到门户。资料文件放在 NAS，门户只登记链接。新闻封面可在后台上传，并应：

- 使用扩展名白名单。
- 限制文件大小。
- 校验文件真实类型。
- 进行恶意文件扫描。
- 对可执行文件进行来源确认。
- 记录文件校验值。
- 禁止把敏感文件放入 Web 根目录。

新闻封面上传以上述规则为基线。

## 10.3 隐私

- 不展示个人手机号、家庭地址、身份证件等信息。
- 不在页面上展示个人联系方式。
- 组织结构只展示工作需要的信息。
- 密码只存哈希。不采集密钥和客户资料，不在页面展示密码。
- 如记录访问日志，应明确用途、保留期限和访问人员。



## 10.4 性能

建议在详细设计阶段确认性能预算：

- 首屏关键内容优先加载。
- 图片按显示尺寸压缩。
- 非首屏图片延迟加载。
- 搜索索引按实际规模控制体积。
- 页面不依赖大型运行时服务。
- 弱网络和普通办公终端可以完成核心任务。



## 10.5 兼容性

- 支持企业规定的主流桌面浏览器版本。
- 支持常见手机浏览器访问。
- 不依赖仅在单一浏览器可用的关键功能。
- 打开资料和外链在浏览器安全策略下行为一致。



## 10.6 可观测性

一期至少具备：

- Nginx 访问和错误日志。
- 容器健康状态。
- 磁盘空间和日志容量监控。
- 域名与证书到期提醒。
- 失效链接定期扫描。
- 发布后核心页面冒烟检查。

如企业允许，可使用隐私友好的访问统计，了解热门入口和零结果查询；统计方案不得采集不必要的个人信息。

## 10.7 备份与恢复

备份对象：

- Git 内容仓库（含 `content/`）
- PostgreSQL（新闻、公告、用户和记住登录凭证）
- 部署配置
- Nginx 镜像
- 发布清单

定期执行恢复演练，确认备份文件可用，而不是只确认备份任务成功。

# 11. 内容治理与发布流程



## 11.1 角色与责任


| 角色      | 主要责任                   |
| ------- | ---------------------- |
| 内容负责人   | 提供内容、确认准确性、版本和适用范围     |
| 内容审核人   | 审核内容表述、制度是否仍适用和发布范围    |
| 门户编辑    | 维护资料字段和页面质量；在后台发布新闻和公告 |
| 安全审核人   | 审核安装包、敏感信息和异常发布内容      |
| 技术发布人   | 构建、部署、回滚和运行检查          |
| 门户产品负责人 | 管理信息架构、规则、优先级和验收       |


同一人可以兼任多个角色，但责任必须明确记录。

## 11.2 发布流程



### 应用、资料和日历

1. 内容负责人提供标题、分类和 NAS 链接。
2. 门户编辑检查标题、分类、文件名、大小、更新时间和链接。
3. 内容审核人确认内容准确和适用范围。
4. 安装包、脚本等高风险链接确认来源。
5. 内容通过 Git 变更提交。
6. 自动执行 Schema、链接和引用检查。
7. 测试环境预览桌面端和移动端。
8. 审核通过后构建并发布生产环境。
9. 发布后检查首页、搜索、详情，并抽查链接可打开。
10. 记录发布版本和结果。



### 新闻和公告

1. 维护人员在后台填写内容。
2. 新闻确认标题、正文和发布日期。公告确认标题、发布日期、置顶和文件链接。
3. 发布后员工端可见。
4. 下线后从首页、列表和搜索中移除。



## 11.3 链接检查

- 资料不设复核日期。
- 发布时抽查资料链接和公告文件可打开。
- 每季度检查失效链接。
- 失效系统必须提供替代入口。



## 11.4 删除

- 不再展示的内容从目录中移除。
- 仍被首页或其他内容引用时，先改引用，再移除。
- 法规、制度和合同相关文件按企业档案规则处理。

| 开放注册被外部邮箱占用    | 无关账号进入门户 | 服务端只接受 `@ggquanta.com`，并先校验人机验证 |
| 栏目重复保存同一资料     | 版本冲突     | 唯一实体 + 稳定 ID 关联                 |
| 搜索承诺包含文件正文     | 用户预期落差   | 明确一期只检索目录元数据                    |
| 多套技术选项长期不决     | 设计和估时反复  | 启动前冻结技术 ADR                     |
| 资料链接失效         | 打开错误文件   | 发布时抽查链接。文件以 NAS 为准              |
| 首页模块过多         | 高频任务被稀释  | 搜索和常用入口优先，限制模块数量                |
| 静态站缺少使用数据      | 无法判断效果   | 任务测试、反馈和合规统计相结合                 |
